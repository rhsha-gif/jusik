# Best-Fit Codex–Claude Collaboration Protocol v1

> 최상위 원칙: **잘하는 건 잘하는 에이전트가 한다.**

이 문서는 Codex/GPT 계열과 Claude Code/Fable/Opus 계열이 한 저장소에서 협업할 때 사용하는 범용
프로토콜이다. 프로젝트별 `AGENTS.md`의 안전 규칙과 사용자 지시는 항상 이 문서보다 우선한다.

`docs/professional_operator_workboard.md`처럼 완료된 과거 작업보드의 소유권·Git 규칙은 해당 미션의
역사 증거일 뿐 새 미션의 권한 규칙이 아니다. 새 미션에서는 루트 `AGENTS.md`, 이 프로토콜, 활성 미션
작업보드가 과거 규칙을 대체한다.

## 1. 기본 운영 모델

1. 사용자의 임무를 처음 받은 에이전트가 `mission lead`가 되고 완료 보고까지 책임진다.
2. 리드는 목표, 성공 조건, 범위, 안전 경계, 작업 그래프를 먼저 작성한다.
3. 상대 에이전트는 구현 전에 작업 분해와 검증 계획을 검토한다.
4. 모든 비단순 미션에서 상대 에이전트는 최소 하나의 **실질 역할**을 독립적으로 소유한다.
5. 작업량을 50:50으로 맞추지 않는다. 적합도와 검증 가능성을 우선한다.
6. 최초 수신자는 지휘권을 유지하되 실제 구현 대부분을 더 적합한 상대에게 위임할 수 있다.

실질 역할은 다음 중 하나여야 한다.

- 독립 구현과 집중 테스트를 포함한 커밋
- 후속 구현을 구속하는 연구, 계약, 설계 또는 위험 매트릭스
- 병합을 차단할 수 있는 적대 테스트나 독립 감사

단순 의견, 진행 상황 확인, 형식적 승인만으로는 실질 역할을 충족하지 않는다. 자연스러운 독립 역할이
전혀 없다면 리드는 그 근거를 작업보드에 기록한다.

## 2. 능력 기반 라우팅

각 구현 작업은 두 에이전트를 다음 기준으로 1점부터 5점까지 평가한다.

| 기준 | 가중치 | 판단 근거 |
|---|---:|---|
| 문제·도메인 적합도 | 30% | 문제 이해, 연구·설계·알고리즘 전문성 |
| 저장소·도구 적합도 | 25% | 로컬 실행, 프레임워크, 운영 도구 접근성 |
| 유사 작업 실적 | 25% | 완료된 유사 작업의 점수표 증거 |
| 문맥 연속성 | 10% | 현재 코드와 결정에 대한 최신 문맥 보유 여부 |
| 인계·충돌 비용 | 10% | 경로 겹침, 통합 난이도, 대기 의존성의 역점수 |

가중 총점은 다음 식으로 계산한다.

```text
fit = domain * 0.30 + tools * 0.25 + track_record * 0.25
    + continuity * 0.10 + coordination * 0.10
```

- 더 높은 점수의 에이전트가 구현을 소유한다.
- 점수 차가 `0.5` 이하이면 최초 수신자 측을 선택해 인계 비용을 줄인다.
- 안전 중요 변경과 다중 모듈 변경은 구현자와 다른 에이전트를 검토자로 둔다.
- 모델 이름과 버전을 기록한다. `Fable`, `Opus`, `GPT`, `Codex`를 하나의 고정 능력으로 합치지 않는다.
- 초기 강점은 선험적 우선순위일 뿐 소유권 제한이 아니다.

초기 우선순위:

- Claude/Fable/Opus: 연구 종합, 퀀트·리스크 설계, 장문 계약, 알고리즘 구현, 적대 테스트와 독립 감사
- Codex/GPT: 저장소 탐색, DB·API·UI·잡 통합, 실행 기반 디버깅, 빌드·테스트 루프, mainline 통합

실제 라우팅에는 [능력 점수표](agent_capability_scorecard.md)를 사용한다.

## 3. 미션 접수와 작업 그래프

리드는 구현 전에 [미션 작업보드 템플릿](agent_workboard_template.md)을 복사해 다음을 확정한다.

- 미션 ID, 최초 수신자, 리드, 사용 모델
- 목표, 범위, 제외 범위, 프로젝트 안전 규칙
- 관찰 가능한 완료 조건과 필수 검증 명령
- 구현·연구·테스트·감사 작업의 의존성 그래프
- 작업별 소유자, 검토자, 적합도 점수, 소유 경로, worktree와 branch
- 통합 순서와 사용자 입력이 필요한 게이트

상태 흐름은 다음과 같다.

```text
proposed -> ready -> in_progress -> review -> integrated -> done
                         |             |
                         +-> blocked <-+
```

- 각 에이전트는 동시에 하나의 `in_progress` 작업만 소유한다.
- `done`은 정확한 검증 출력과 통합 커밋이 기록된 뒤에만 허용한다.
- 읽기 전용 조사도 결과가 다른 작업의 결정을 구속하면 별도 작업으로 기록한다.

## 4. Claude Code/Fable5 작업 신호

Claude 작업이 `ready`가 되는 즉시 리드는 사용자에게 다음 형식으로 알린다.

```text
🔔 Claude Code/Fable5 작업 시점
- 작업 ID: <task-id>
- 소유 경로: <paths>
- 완료 조건: <acceptance>
- Codex 병렬 작업: <independent task or none>
```

이 알림은 승인 요청이 아니다. 저장소 내부의 읽기·코드·테스트·문서 작업은 자동으로 진행한다. 범위 확대,
외부 시스템 변경, 비밀 접근, 거래 권한 변경처럼 새 권한이 필요한 경우에만 사용자 응답을 기다린다.
Codex 작업이 Claude 리드 아래 `ready`가 될 때도 같은 형식으로 대칭 통지한다.

## 5. Worktree, branch, commit

- Codex 작업: `codex/<mission-id>-<task-id>`
- Claude 작업: `claude/<mission-id>-<task-id>`
- 각 작업은 별도 worktree를 사용하고 작업보드에 절대 경로를 기록한다.
- 서로 다른 활성 작업은 소유 경로가 겹치면 안 된다.
- 각 에이전트는 자기 worktree에서 자기 경로만 stage하고 커밋한다.
- 기존 사용자 변경을 복사, 정리, stash, reset 또는 커밋하지 않는다.
- 미션 리드만 mainline을 통합한다. 상대 커밋을 diff 검토한 뒤 merge 또는 cherry-pick한다.
- 통합자는 프로젝트 필수 전체 검증을 깨끗한 커밋 상태에서 다시 실행한다.

커밋 인계에는 다음이 필요하다.

```text
task_id:
agent_and_model:
commit:
owned_paths:
acceptance_met:
exact_checks:
known_limits:
integration_requests:
```

## 6. 리뷰, 충돌, 실패 전환

설계 판단이 충돌하면 다음 순서로 해결한다.

1. 양쪽이 코드, 테스트, 공식 문서 또는 재현 가능한 관찰을 제시한다.
2. 안전하고 작은 실험으로 비교할 수 있으면 리드가 실험을 실행한다.
3. 미션 리드가 결과와 선택 근거를 작업보드에 기록하고 결정한다.
4. 범위 확대, 외부 상태 변경, 거래·비밀 관련 결정만 사용자에게 올린다.

같은 원인의 테스트 실패나 결함이 두 번 반복되면 소유자는 추가 수정을 멈춘다. 상대 에이전트가 읽기 전용
진단을 작성한 뒤 소유자가 한 번만 더 수정한다. 같은 문제가 다시 실패하면 작업을 재배정하거나 사용자에게
에스컬레이션한다.

검토자는 P0/P1 결함을 발견하면 병합을 차단한다. 구현자는 자기 안전 중요 변경을 최종 승인할 수 없다.

## 7. 능력 점수의 발전

각 완료 작업은 점수표에 원시 증거와 1~5 등급을 기록한다.

- `5`: 최초 검증 통과, P0/P1 없음, 필수 검증 모두 성공
- `4`: 경미한 재작업 1회, P0/P1 없음
- `3`: 복수의 경미한 재작업 후 성공
- `2`: 중대 결함 또는 담당 재배정
- `1`: 작업 실패 또는 안전 결함 유발

같은 작업군의 비교 가능한 표본이 3개 이상 쌓인 뒤에만 선호 담당을 바꾼다. P0/P1 안전 결함은 표본 수와
관계없이 즉시 해당 작업군의 우선순위를 재검토한다. 속도만으로 품질보다 높은 점수를 줄 수 없다.

## 8. 프로젝트 안전 어댑터

이 프로토콜은 프로젝트의 안전 경계를 넓히지 않는다. QuantPilot에서는 다음이 항상 유지된다.

- live trading과 market order는 기본 비활성
- 비밀, 자격증명, 개인 계좌 정보는 저장소에 기록하지 않음
- 외부 커넥터 단위 테스트는 fake client와 오프라인 fixture 사용
- risk gate, kill switch, idempotency, order state machine, audit, reconciliation 우회 금지
- 거래·비밀·외부 상태 변경은 사용자 승인 없이는 실행하지 않음

구체적인 프로젝트 명령과 안전 불변식은 루트 `AGENTS.md`를 따른다.

## 9. Tabletop acceptance scenarios

| Scenario | Expected protocol result |
|---|---|
| Codex가 상태 저장 기능을 접수 | Codex가 리드를 유지하고 적합도 우위 시 구현을 맡으며 Claude는 계약 또는 적대 테스트를 독립 소유한다. |
| Claude가 퀀트 전략 기능을 접수 | Claude가 리드와 알고리즘 구현을 맡고 Codex는 저장소 통합 또는 전체 실행 검증을 독립 소유한다. |
| UI와 외부 연구가 섞인 기능 | 연구와 구현을 점수별로 분리하고 겹치지 않는 worktree에서 병렬 실행한다. |
| 같은 결함이 두 번 반복 | 소유자는 수정을 멈추고 상대 진단을 받는다. 진단 후 다시 실패하면 재배정 또는 사용자 에스컬레이션한다. |
| main workspace에 사용자 dirty 파일 존재 | 깨끗한 기준 commit에서 별도 worktree를 만들고 사용자 파일을 복사, 정리, stage 또는 commit하지 않는다. |

위 다섯 결과 중 하나라도 작업보드에 표현할 수 없거나 어댑터 규칙과 충돌하면 프로토콜 변경을 완료로
간주하지 않는다.
